## 1. Базовая теория: Что такое Redis и почему он такой быстрый?

### 🎙️ Вопрос Тимлида: *"Что такое Redis, для каких задач он подходит и за счет чего он работает настолько быстро?"*

**💡 Твой ответ (как сказать правильно):**
> **«Redis (Remote Dictionary Server)** — это нереляционная (NoSQL) In-Memory база данных, работающая по принципу «ключ-значение». Поскольку все данные хранятся непосредственно в оперативной памяти (RAM), операции чтения и записи выполняются за доли миллисекунд (субмиллисекундная задержка).
>
> **Главные причины невероятной скорости Redis:**
> 1. **Хранение в RAM (In-Memory)**: Доступ к оперативной памяти на порядки быстрее, чем обращение к SSD или HDD дискам.
> 2. **Однопоточная архитектура (Single-Threaded Event Loop)**: Redis выполняет команды последовательно в одном основном потоке. Это полностью исключает накладные расходы на создание потоков, переключение контекста (context switching), а главное — исключает состояние гонки (race conditions) и необходимость в сложных блокировках (locks/mutexes).
> 3. **Неблокирующий ввод-вывод (I/O Multiplexing)**: Сетевые запросы обрабатываются через системные вызовы вроде `epoll` (в Linux), позволяя одному потоку эффективно обслуживать десятки тысяч одновременных соединений».

### 📋 Ключевые термины, которые нужно знать:
1. **TTL (Time To Live)** — время жизни ключа в секундах или миллисекундах. После истечения этого времени Redis автоматически удаляет ключ.
2. **Eviction (Вытеснение)** — процесс удаления ключей из памяти, когда Redis достигает лимита выделенной RAM (`maxmemory`), согласно выбранной политике (например, LRU или LFU).
3. **RESP (REdis Serialization Protocol)** — бинарно-безопасный текстовый протокол, по которому клиенты общаются с сервером Redis.

## 2. Структуры данных в Redis

На собеседованиях часто просят перечислить типы данных Redis и привести примеры их использования.

```
                       КЛЮЧ (String, например "user:100")
                                      │
         ┌──────────────┬─────────────┼─────────────┬──────────────┐
         ▼              ▼             ▼             ▼              ▼
     STRINGS          LISTS         SETS         HASHES       SORTED SETS
   [ "Sofia" ]    [ A -> B -> C ]  [A, B, C]  [name: "Sofia"  [A: 10, B: 20]
  Простой кэш,      Очереди,     Уникальные   field: value]   Рейтинги, лимиты,
  сессии, TTL     история логов    теги, ID    Хранение JSON-   планировщики
                                                 объектов
```

### 🎙️ Вопрос Тимлида: *"Какие структуры данных есть в Redis и как их применить на практике?"*

**💡 Твой ответ:**
> «Redis — это не просто база ключ-строка, это сервер структур данных. Вот основные из них:
>
> 1. **Strings (Строки)**: Базовый тип, может хранить текст, сериализованный JSON или даже бинарные данные (до 512 МБ).
>    * *Применение*: Кэширование ответов API, хранение сессий, счетчики (команды `INCR/DECR`).
> 2. **Hashes (Хэши)**: Карта пар "поле-значение" (аналог Java `Map<String, String>`).
>    * *Применение*: Хранение объектов с набором свойств (например, профиль пользователя: `name`, `email`, `role`). Позволяет обновлять отдельные поля без перезаписи всего объекта.
> 3. **Lists (Списки)**: Связные списки строк (сохраняют порядок вставки).
>    * *Применение*: Простые очереди сообщений (команды `LPUSH` и `BRPOP` для FIFO-очереди).
> 4. **Sets (Множества)**: Неупорядоченные коллекции уникальных строк. Поддерживают операции пересечения, объединения и разности.
>    * *Применение*: Список уникальных подписчиков, теги вакансий, проверка нахождения в черном списке.
> 5. **Sorted Sets (ZSet — Упорядоченные множества)**: Множества, где каждый элемент связан с числовым весом (score). Элементы автоматически сортируются по этому весу.
>    * *Применение*: Лидерборды (leaderboards), очереди с приоритетами, Rate Limiting (ограничение частоты запросов по скользящему окну)».

## 3. Реализация в CareerPilot AI: Отказоустойчивое кэширование (Resilient Cache)

В проекте CareerPilot AI мы настроили Redis для кэширования тяжелых ответов AI-ассистента (подсказки к резюме, генерация сопроводительных писем). Время работы LLM-модели (Ollama/OpenAI) может достигать 5–15 секунд, поэтому кэширование критически важно.

### 🎙️ Вопрос Тимлида: *"Как вы настроили кэширование в Spring Boot и что произойдет, если сервер Redis внезапно упадет (Connection Refused)?"*

**💡 Твой ответ (показывает высокий уровень инженерной мысли):**
> «В CareerPilot AI мы подключили стартер `spring-boot-starter-data-redis` и использовали декларативное кэширование Spring Cache через аннотацию `@Cacheable`.
>
> Но в базовой конфигурации Spring Cache таится серьезный риск: **если Redis упадет, любой запрос к кэшированному методу выбросит `QueryTimeoutException` или `RedisConnectionFailureException`, и всё приложение сломается.**
>
> Чтобы этого избежать, я реализовал паттерн **Resilient Cache (Отказоустойчивый кэш)**. Я создал кастомный класс конфигурации `CacheConfig`, который имплементирует интерфейс `CachingConfigurer` и переопределяет метод `errorHandler()`:»

```java
package com.alexanderpolozhnov.careerpilot.config;

import lombok.extern.slf4j.Slf4j;
import org.springframework.cache.Cache;
import org.springframework.cache.annotation.CachingConfigurer;
import org.springframework.cache.interceptor.CacheErrorHandler;
import org.springframework.context.annotation.Configuration;

@Slf4j
@Configuration
public class CacheConfig implements CachingConfigurer {

    @Override
    public CacheErrorHandler errorHandler() {
        return new CacheErrorHandler() {
            @Override
            public void handleCacheGetError(RuntimeException exception, Cache cache, Object key) {
                // Если Redis недоступен при чтении — логируем ошибку и позволяем выполнить оригинальный метод (запрос к LLM/БД)
                log.error("Cache GET error for key {}: {}. Falling back to original method.", key, exception.getMessage());
            }

            @Override
            public void handleCachePutError(RuntimeException exception, Cache cache, Object key, Object value) {
                log.error("Cache PUT error for key {}: {}", key, exception.getMessage());
            }

            @Override
            public void handleCacheEvictError(RuntimeException exception, Cache cache, Object key) {
                log.error("Cache EVICT error for key {}: {}", key, exception.getMessage());
            }

            @Override
            public void handleCacheClearError(RuntimeException exception, Cache cache) {
                log.error("Cache CLEAR error: {}", exception.getMessage());
            }
        };
    }
}
```

> «Благодаря этому `CacheErrorHandler` наше приложение полностью защищено от сбоев кэша. Если контейнер Redis отключится или перезагрузится, приложение продолжит стабильно работать, просто прозрачно переключится на прямой вызов оригинальных методов (запросы пойдут напрямую в базу данных или к LLM-модели), а в логах мы увидим предупреждения».

## 4. Как Redis сохраняет данные на диск (Persistence)

Поскольку оперативная память энергозависима, при перезагрузке сервера Redis все данные сотрутся. Чтобы этого не происходило, в Redis есть механизмы персистентности.

### 🎙️ Вопрос Тимлида: *"Как устроено сохранение данных на диск в Redis? В чем разница между RDB и AOF?"*

**💡 Твой ответ:**
> «Redis предлагает два основных механизма персистентности, которые можно использовать как по отдельности, так и вместе:
>
> 1. **RDB (Redis Database Backup / Снапшоты)**:
>    * *Принцип*: С определенным интервалом времени (например, раз в 5 минут или если изменилось более 100 ключей) Redis делает полный снимок (снапшот) всей базы данных в памяти и записывает его в один файл `dump.rdb`.
>    * *Плюсы*: Файл очень компактный, база восстанавливается мгновенно, практически нет накладных расходов на производительность (запись делает дочерний процесс через `fork()`).
>    * *Минусы*: Есть риск потери данных за последний интервал времени (если Redis упадет между созданием снапшотов).
> 
> 2. **AOF (Append Only File / Лог транзакций)**:
>    * *Принцип*: Каждая полученная команда записи (write) записывается в конец файла `appendonly.aof` в реальном времени. Раз в секунду (настройка `everysec`) Spring/Redis делает сброс буфера на диск (`fsync`).
>    * *Плюсы*: Максимальная надежность (риск потери данных — максимум за 1 секунду).
>    * *Минусы*: Файл быстро разрастается, восстановление базы занимает больше времени, чуть ниже производительность из-за постоянной работы с диском.
>
> **Как использовать в продакшене:**
> Лучшая практика (и стандарт по умолчанию во многих системах) — **совместное использование RDB + AOF**. RDB используется для быстрого старта и резервного копирования, а AOF — для гарантии сохранности данных между снапшотами».

## 5. Политики вытеснения памяти (Eviction Policies)

Когда память, выделенная под Redis (`maxmemory`), заполняется на 100%, Redis должен решить, как обрабатывать новые запросы на запись.

### 🎙️ Вопрос Тимлида: *"Что происходит, когда в Redis заканчивается память? Какие политики Eviction вы знаете?"*

**💡 Твой ответ:**
> «Если память заполнилась, Redis начинает вытеснять старые ключи согласно политике, настроенной в параметре `maxmemory-policy`. 
> Основные политики делятся на три семейства:
>
> 1. **noeviction (по умолчанию)**: Redis просто возвращает ошибку `OOM command not allowed when used memory > 'maxmemory'` на все новые запросы на запись. Чтение продолжает работать. Подходит, если Redis используется как полноценная база данных, где потеря данных недопустима.
> 2. **LRU (Least Recently Used)**: Удаляет ключи, которые использовались **дольше всего назад** (самые "старые" по времени последнего доступа).
>    * `allkeys-lru`: Ищет кандидатов по всей базе. (Рекомендуется для обычного кэша).
>    * `volatile-lru`: Ищет кандидатов только среди ключей, у которых задан TTL.
> 3. **LFU (Least Frequently Used)**: Удаляет ключи, которые использовались **реже всего** (самая низкая частота обращений за последнее время).
>    * `allkeys-lfu` / `volatile-lfu`.
> 4. **Random**: Случайное удаление ключей (`allkeys-random` / `volatile-random`).
> 5. **volatile-ttl**: Удаляет ключи, у которых самый маленький оставшийся срок жизни (TTL)».

## 6. Масштабирование Redis в продакшене

### 🎙️ Вопрос Тимлида: *"Как вы будете масштабировать Redis, если нагрузка или объем данных вырастут в десятки раз?"*

**💡 Твой ответ:**
> «Для масштабирования Redis используются три основных архитектурных паттерна в зависимости от целей:
>
> 1. **Репликация (Master-Replica)**:
>    * *Цель*: Масштабирование чтения и отказоустойчивость.
>    * *Как устроено*: Есть один Master (куда идут все записи) и несколько Replicas (которые копируют данные с мастера). Все запросы на чтение распределяются по репликам.
> 2. **Redis Sentinel (Высокая доступность / Failover)**:
>    * *Цель*: Автоматическое управление сбоями в схеме репликации.
>    * *Как устроено*: Набор специальных легковесных процессов (Sentinels) мониторит работу Master и Replicas. Если Master падает, Sentinel-ы путем голосования (консенсуса) выбирают одну из реплик и автоматически "повышают" её до нового Master-а, перенаправляя трафик приложения.
> 3. **Redis Cluster (Горизонтальное масштабирование / Шардирование)**:
>    * *Цель*: Масштабирование записи и хранение объемов данных, не влезающих в RAM одного сервера.
>    * *Как устроено*: Данные автоматически шардируются (разделяются) между несколькими мастерами. Redis Cluster делит пространство ключей на **16384 хэш-слота (hash slots)**. При записи ключа вычисляется хэш `CRC16(key) % 16384`, определяющий, на какой именно физический сервер (шард) отправится этот ключ».

## 7. Продвинутые вопросы и "Ловушки" на собеседованиях

Вот темы, на которых сыплются многие разработчики. Прочитай их внимательно!

### 🔥 Тонкость №1: Проблема "KEYS \*" в продакшене (Блокировка потока)
* **Тимлид спрашивает:** *"Нам нужно найти все ключи кэша, начинающиеся на `user:`. Разработчик предлагает выполнить команду `KEYS user:*`. Почему за такое предложение в продакшене оторвут руки?"*
* **Ты отвечаешь:**
  > «Команда `KEYS` имеет вычислительную сложность **O(N)**, где N — общее количество ключей в базе данных. Поскольку Redis является **однопоточным**, выполнение команды `KEYS` на большой базе (миллионы ключей) заблокирует этот единственный поток на несколько секунд (или даже минут). 
  > В это время Redis не сможет обработать ни один другой запрос. Все подключения клиентов начнут падать по таймауту, что приведет к полному отказу приложения (DDoS изнутри).
  >
  > **Как сделать правильно**: Использовать команду **`SCAN`**. Она работает итеративно (через курсор), возвращая ключи небольшими порциями (например, по 10-100 штук за шаг). Она не блокирует основной поток Redis и безопасна для использования в продакшене».

---

### 🔥 Тонкость №2: Лавина кэша (Cache Avalanche)
* **Тимлид спрашивает:** *"Что такое лавина кэша, чем она опасна и как её предотвратить?"*
* **Ты отвечаешь:**
  > «**Cache Avalanche** — это ситуация, когда в один и тот же момент времени истекает срок жизни (TTL) у огромного количества популярных ключей, либо когда сам сервер Redis падает.
  >
  > В этот миг все входящие запросы пользователей не находят данных в кэше и одновременно летят напрямую в основную базу данных (PostgreSQL). Реляционная БД не справляется с терабайтами внезапного параллельного трафика, у неё заканчивается пул соединений, и база "ложится".
  >
  > **Как предотвратить:**
  > 1. **Разброс TTL (Jitter)**: Никогда не ставить одинаковый жесткий TTL для множества ключей. К базовому TTL нужно добавлять случайное смещение (например, `TTL = 24 часа + random(1, 30) минут`). Это размажет время удаления ключей во времени.
  > 2. **Отказоустойчивые конфигурации**: Использовать Redis Sentinel / Cluster, а также паттерн **Resilient Cache** (с `CacheErrorHandler`), чтобы падение кэша не ломало бэкенд».

### 🔥 Тонкость №3: Пробитие кэша (Cache Penetration)
* **Тимлид спрашивает:** *"Что такое пробитие кэша? Как злоумышленник может использовать это для атаки на нашу систему?"*
* **Ты отвечаешь:**
  > «**Cache Penetration** — это ситуация, когда клиенты запрашивают данные, которых **физически нет ни в кэше, ни в базе данных** (например, обращение к несуществующему пользователю `/api/users/9999999`).
  >
  > Так как данных нет, кэш отвечает "промахом" (miss), и запрос каждый раз перенаправляется в БД. Злоумышленник может запустить цикл генерации случайных несуществующих ID, совершив атаку на базу данных в обход кэша.
  >
  > **Как предотвратить:**
  > 1. **Кэширование пустых значений (Cache Nulls)**: Если БД вернула пустой результат (`null`), мы все равно записываем этот `null` в Redis с коротким TTL (например, на 1-2 минуты). При повторном запросе Redis сразу вернет "пусто", не дергая базу данных.
  > 2. **Фильтр Блума (Bloom Filter)**: Компактная вероятностная структура данных, которая позволяет быстро и со 100% точностью ответить, что **элемента гарантированно нет в базе данных**. Запрос отсекается на уровне фильтра Блума еще до обращения к Redis или БД».

### 🔥 Тонкость №4: Сериализация в Spring Boot (JDK vs JSON)
* **Тимлид спрашивает:** *"Какой сериализатор для кэша вы использовали в Spring Boot? Какие проблемы возникают при настройках по умолчанию?"*
* **Ты отвечаешь:**
  > «По умолчанию Spring Boot Redis использует **`JdkSerializationRedisSerializer`**. 
  > 
  > **Две проблемы дефолтного сериализатора:**
  > 1. **Нечитаемые данные в Redis**: Ключи и значения записываются в бинарном формате с префиксами вроде `\xac\xed\x00\x05t\x00\x0f`. Если зайти в Redis через консоль CLI или интерфейс, невозможно понять, что там лежит.
  > 2. **Проблемы версионирования**: Если мы изменим класс Java (добавим поле или переименуем его), старый закэшированный бинарный объект в Redis при десериализации выбросит `InvalidClassException` из-за несовпадения `serialVersionUID`.
  >
  > **Как сделать правильно**: Использовать **`GenericJackson2JsonRedisSerializer`** (или `Jackson2JsonRedisSerializer`). Он сериализует объекты в чистый, читаемый JSON. Это позволяет легко анализировать кэш глазами, а также безопасно обновлять поля в классах (Jackson просто проигнорирует новые или отсутствующие поля при десериализации)».
