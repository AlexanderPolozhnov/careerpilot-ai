# Блок 1. Java Core

### 1. How to create a thread? (Как создать поток?)
В Java есть три основных способа создания потока:
1. **Унаследоваться от класса `Thread`** и переопределить метод `run()`:
   ```java
   class MyThread extends Thread {
       public void run() { System.out.println("Thread is running"); }
   }
   new MyThread().start(); // Важно: вызываем start(), а не run()!
   ```
2. **Реализовать интерфейс `Runnable`** и передать его в конструктор `Thread` (более предпочтительный способ, так как Java не поддерживает множественное наследование):
   ```java
   Runnable task = () -> System.out.println("Thread is running");
   new Thread(task).start();
   ```
3. **Реализовать интерфейс `Callable<V>`** (через пул потоков `ExecutorService`). Метод `call()` в отличие от `run()` может возвращать результат типа `Future` и выбрасывать проверяемые исключения (Checked Exceptions).

### 2. What is the difference between primitive and reference data types? (Разница между примитивными и ссылочными типами?)
* **Примитивные типы (8 штук)**: `byte`, `short`, `int`, `long`, `float`, `double`, `char`, `boolean`.
  * Хранят свои фактические значения непосредственно в **Стеке (Stack)**.
  * Не являются объектами, у них нет методов, полей и они не могут быть `null`.
  * Передаются в методы **по значению** (копируется само значение).
* **Ссылочные типы**: Классы, интерфейсы, массивы, перечисления (например, `String`, `Integer`, `MyClass`).
  * Сами объекты хранятся в **Куче (Heap)**, а в **Стеке (Stack)** хранится только ссылка (адрес в памяти) на этот объект.
  * Могут принимать значение `null`, имеют методы и поддерживают наследование.
  * Ссылки передаются в методы **по значению** (копируется адрес ссылки, то есть мы все равно работаем с тем же объектом в куче).

### 3. What can the final keyword be applied to? (К чему применим final?)
Ключевое слово `final` означает неизменяемость и применяется к:
1. **Переменным**: Переменная может быть инициализирована только один раз. Попытка изменить её значение (или переназначить ссылку для ссылочного типа) вызовет ошибку компиляции. *Важно: если переменная ссылается на объект, сам объект менять можно (например, добавлять элементы в final-список), нельзя менять только саму ссылку*.
2. **Методам**: Метод не может быть переопределен (overridden) в классах-наследниках.
3. **Классам**: От класса нельзя унаследоваться (например, класс `String` является `final`).

### 4. What is static and why is it needed? (Что такое static и зачем нужен?)
Модификатор `static` связывает поле или метод с **самим классом**, а не с его конкретными объектами (экземплярами).
* **Статические поля**: Общие для всех объектов класса. Хранятся в памяти один раз (в Metaspace).
* **Статические методы**: Могут быть вызваны без создания объекта класса (например, `Math.sqrt()`). Они могут обращаться только к другим статическим полям и методам класса (у них нет доступа к `this`).
* **Статические блоки**: Выполняются один раз при первой загрузке класса JVM в память (до создания объектов и вызова конструктора).
* **Статические вложенные классы**: Не имеют доступа к нестатическим полям внешнего класса.

### 5. What is a functional interface? Name the popular ones (Функциональный интерфейс и примеры)
**Функциональный интерфейс** — это интерфейс, который содержит ровно **один абстрактный метод** (может содержать сколько угодно `default` или `static` методов). Помечается аннотацией `@FunctionalInterface` (необязательно, но помогает избежать ошибок). Используется как основа для лямбда-выражений.

**Популярные интерфейсы из пакета `java.util.function`:**
1. `Consumer<T>` — принимает `T`, ничего не возвращает (`void accept(T t)`).
2. `Producer` / `Supplier<T>` — ничего не принимает, возвращает `T` (`T get()`).
3. `Function<T, R>` — принимает `T`, возвращает `R` (`R apply(T t)`).
4. `Predicate<T>` — принимает `T`, возвращает `boolean` (`boolean test(T t)`).
5. `UnaryOperator<T>` — принимает `T`, возвращает `T` (`T apply(T t)`).
6. `BinaryOperator<T>` — принимает два `T`, возвращает `T`.

### 6. What is a terminal function? (Что такое терминальная операция?)
В Stream API операции делятся на **промежуточные** (intermediate) и **терминальные** (terminal).
* Промежуточные операции (`filter`, `map`, `sorted`) ленивы — они не выполняют никакой работы, пока не вызвана терминальная операция, и возвращают новый стрим.
* **Терминальная операция** (`collect`, `forEach`, `reduce`, `count`, `findFirst`) запускает обработку данных в стриме, закрывает его и возвращает конечный результат (объект, коллекцию, число) или ничего (`void`). Стрим нельзя использовать повторно после вызова терминальной операции.

---

### 7. Map vs flatMap stream API
* **`map(Function<T, R>)`**: Преобразует каждый элемент стрима типа `T` в один элемент типа `R` (связь 1-к-1). Возвращает стрим объектов `Stream<R>`.
  * *Пример*: Преобразовать список строк в их длины: `["a", "bb"] -> [1, 2]`.
* **`flatMap(Function<T, Stream<R>>)`**: Преобразует каждый элемент `T` в целый *стрим* элементов `R`, а затем «схлопывает» (объединяет) все полученные стримы в один плоский стрим (связь 1-ко-многим).
  * *Пример*: Преобразовать список списков `[[1, 2], [3, 4]]` в плоский список `[1, 2, 3, 4]`.

### 8. OOP principles (Принципы ООП)
1. **Абстракция**: Выделение ключевых характеристик объекта и игнорирование несущественных деталей. Реализуется через интерфейсы и абстрактные классы.
2. **Инкапсуляция**: Сокрытие внутренней реализации объекта и предоставление доступа к ней только через публичный интерфейс (геттеры/сеттеры, модификаторы доступа `private`/`protected`).
3. **Наследование**: Возможность создать новый класс на основе существующего, переняв его свойства и методы, что исключает дублирование кода.
4. **Полиморфизм**: Возможность объектов с разной реализацией иметь один и тот же интерфейс. Бывает двух видов:
   * *Динамический (Overriding)* — переопределение методов в наследниках (полиморфизм времени выполнения).
   * *Статический (Overloading)* — перегрузка методов с одинаковыми именами, но разными параметрами (полиморфизм времени компиляции).

### 9. Contract equals and hashcode (Контракт equals и hashCode)
Если мы переопределяем `equals()`, мы **обязаны** переопределить `hashCode()`. Их связь строится на правилах:
1. Если два объекта **равны** по `equals()`, их `hashCode()` **обязан быть одинаковым**.
2. Если `hashCode()` у двух объектов **одинаковый**, это не значит, что они равны по `equals()` (это называется *коллизией*).
3. Если `hashCode()` объектов **разный**, то объекты **гарантированно не равны** по `equals()`.
4. `equals()` должен быть: *рефлексивным* ($x=x$), *симметричным* (если $x=y$, то $y=x$), *транзитивным* (если $x=y$ и $y=z$, то $x=z$), *согласованным* (многократные вызовы дают один результат), и сравнение с `null` всегда дает `false`.

### 10. How does inheritance work in java? (Как устроено наследование в Java?)
* Java поддерживает **одиночное наследование классов** (класс может иметь только одного прямого предка) через ключевое слово `extends`. Это сделано для избежания "смертельного ромба наследования" (diamond problem).
* Множественное наследование реализовано через **интерфейсы** (класс может реализовывать множество интерфейсов через `implements`).
* Все классы в Java неявно наследуются от базового класса `Object`.
* Конструкторы не наследуются. При создании объекта наследника сначала неявно (или явно через `super()`) вызывается конструктор суперкласса.

### 11. What are generic types and why are they needed? (Что такое дженерики и зачем нужны?)
**Generics (Обобщения)** — это параметризованные типы. Они позволяют создавать классы, интерфейсы и методы, где тип обрабатываемых данных указывается как параметр (например, `List<String>`).
* **Зачем нужны**:
  1. **Strict Type Safety (Строгая типизация)** — проверка типов на этапе компиляции, а не в рантайме.
  2. **Исключение явного приведения типов** (Cast) в коде: вместо `(String) list.get(0)` мы пишем `list.get(0)`.
  3. **Type Erasure (Стирание типов)**: Для обратной совместимости в рантайме все дженерики стираются до типа `Object` (или до их верхней границы `extends`), а компилятор сам расставляет касты типов.

### 12. Methods of the Object class. Name them and tell why they are needed (Методы класса Object)
1. `getClass()` — возвращает метаданные класса объекта (`Class<?>`) в рантайме.
2. `equals(Object obj)` — логическое сравнение двух объектов (по умолчанию сравнивает ссылки `==`).
3. `hashCode()` — возвращает числовое представление (хэш-код) объекта.
4. `toString()` — возвращает строковое представление объекта (по умолчанию `ИмяКласса@хэшкод`).
5. `clone()` — создает копию объекта (требует имплементации интерфейса `Cloneable`).
6. `finalize()` — (устарел/deprecated) вызывался сборщиком мусора перед уничтожением объекта.
7. `wait()`, `notify()`, `notifyAll()` — методы для синхронизации потоков (монитора).

### 13. The most popular GCs and general algorithm of work (Популярные сборщики мусора и алгоритмы)
**Общий алгоритм**: Память Кучи (Heap) делится на поколения: **Young Generation** (Эдем/Eden, выжившие/Survivor spaces S0, S1) и **Old Generation**. Большинство объектов живут недолго и умирают в Young Gen. Выжившие объекты после нескольких циклов сборки перемещаются в Old Gen. Сборка идет по принципу трассировки: GC ищет доступные объекты от корневых точек (GC Roots), а недоступные удаляет.

**Популярные GC:**
1. **Serial GC** — однопоточный сборщик для небольших систем. Останавливает все потоки приложения (Stop-the-World, STW).
2. **Parallel GC** — многопоточный сборщик для Young/Old поколений. Нацелен на высокую пропускную способность, но имеет заметные паузы STW.
3. **G1 (Garbage First)** — (дефолтный с Java 9). Делит кучу на сотни мелких регионов. Сначала очищает те регионы, где больше всего мусора (отсюда и название). Минимизирует паузы STW.
4. **ZGC / Shenandoah** — ультрасовременные масштабируемые сборщики с низким временем задержки (паузы STW измеряются микросекундами независимо от размера кучи в терабайты).

### 14. What is try-with-resources and why is it needed?
Конструкция, появившаяся в Java 7, для автоматического закрытия ресурсов (файлов, сетевых сокетов, подключений к БД).
* Ресурс должен реализовывать интерфейс **`AutoCloseable`** (или `Closeable`).
* Записывается как `try (BufferedReader br = new BufferedReader(...)) { ... }`.
* **Зачем нужна**: Избавляет от громоздких блоков `finally` с ручным вызовом `.close()` и исключает утечки памяти (resource leaks), если при работе с ресурсом возникло исключение.

### 15. Integer pool and String pool. What is it and why is it necessary?
Оба механизма созданы для оптимизации памяти и производительности за счет повторного использования неизменяемых (immutable) объектов.
* **String Pool (Пул строк)** — область в куче (Heap), где хранятся уникальные строковые литералы. Если мы пишем `String s1 = "Java"`, строка берется из пула. Если пишем `new String("Java")`, создается новый объект вне пула. Метод `.intern()` позволяет принудительно положить строку в пул.
* **Integer Pool (Пул целых чисел)** — кэширует объекты-обертки `Integer` в диапазоне от **`-128` до `127`** (верхнюю границу можно настроить). При вызове `Integer.valueOf(10)` или автобоксинге `Integer x = 10` объект берется из кэша. Поэтому `Integer a = 127; Integer b = 127; a == b` вернет `true`, а для `128` вернет `false`.

### 16. Stack and Heap, what is stored and where (Стек и Куча)
* **Stack (Стек)**:
  * Область памяти, создаваемая для каждого потока отдельно (Thread-safe).
  * Работает по принципу LIFO (Last In, First Out). Память выделяется и освобождается автоматически при входе/выходе из методов.
  * *Что хранится*: Локальные переменные примитивных типов, ссылки на объекты в куче, вызовы методов (фреймы стека).
* **Heap (Куча)**:
  * Общая область памяти для всего приложения (не является потокобезопасной). Намного больше стека.
  * Памятью управляет Garbage Collector (Сборщик мусора).
  * *What is stored*: Все объекты, массивы, переменные экземпляров классов (поля объектов), String Pool, метаданные классов (Metaspace).

### 17. Popular thread-safe collections. Name and tell how they work (Потокобезопасные коллекции)
1. **`ConcurrentHashMap`**: Вместо блокировки всей таблицы (как в старом `Hashtable`), использует блокировку на уровне отдельных бакетов (корзин/сегментов) с помощью CAS (Compare-And-Swap) и Node-синхронизации. Чтение происходит без блокировок.
2. **`CopyOnWriteArrayList`**: Любая операция модификации (add, set, remove) создает полную копию внутреннего массива. Подходит для сценариев, где чтений в тысячи раз больше, чем записей (так как операции записи очень дорогие). Чтение всегда идет без блокировок.
3. **`ConcurrentLinkedQueue` / `LinkedBlockingQueue`**: Потокобезопасные очереди. Использованы неблокирующие алгоритмы на основе CAS или раздельные блокировки для головы (take) и хвоста (put) очереди.

### 18. HashMap algorithm (Как устроена HashMap?)
Основана на хэшировании. Состоит из массива бакетов (корзин) `Node<K,V>[]`.
1. **Добавление (put)**: Вычисляется `hash(key)`. Индекс бакета определяется как `hash & (n-1)` (где `n` — размер массива).
2. **Коллизии (Collision)**: Если бакет пуст, создается новая Node. Если в бакете уже есть элементы, они выстраиваются в **Односвязный список**.
3. **Разрешение коллизий / Реализация (с Java 8)**: 
   * Если длина списка коллизий в одном бакете превышает **8** элементов, а размер всей HashMap больше или равен **64**, односвязный список преобразуется в **Красно-черное дерево (Red-Black Tree)**. Это ускоряет поиск с худшего времени $O(N)$ до $O(\log N)$.
4. **Ресайз (Resize)**: Когда количество элементов превышает `capacity * loadFactor` (по умолчанию `loadFactor = 0.75`), массив увеличивается в 2 раза, и все элементы пересчитываются на новые индексы (rehashing).

### 19. Differences between ArrayList and LinkedList. What and when works faster
* **`ArrayList`**: Основан на динамическом массиве.
  * *Поиск*: По индексу работает за $O(1)$ (мгновенно). По значению — $O(N)$.
  * *Вставка/Удаление*: В конец — $O(1)$ амортизированное. В середину/начало — $O(N)$, так как требуется сдвигать элементы массива.
* **`LinkedList`**: Основан на двусвязном списке (каждый узел хранит ссылки на предыдущий и следующий узлы).
  * *Поиск*: По индексу работает за $O(N)$ (нужно пройти по цепочке от начала или конца).
  * *Вставка/Удаление*: Если узел уже найден, сама вставка/удаление работает за $O(1)$. Но поиск места вставки занимает $O(N)$.
* **Что быстрее**: `ArrayList` почти всегда быстрее в реальных задачах из-за последовательного расположения в памяти (CPU Cache friendly). `LinkedList` тратит много памяти на хранение ссылок (`prev`, `next`) и создает нагрузку на GC.

### 20. How do TreeMap and TreeSet work?
* **`TreeMap`**: Реализует интерфейс `SortedMap`. Внутри построена на **Красно-черном самобалансирующемся дереве**. Элементы всегда отсортированы по ключу в естественном порядке (через `Comparable`) или с помощью переданного `Comparator`. Операции поиска, вставки и удаления работают за гарантированное время $O(\log N)$. Ключи не могут быть `null`.
* **`TreeSet`**: Внутри использует `TreeMap` (где элементы множества хранятся как ключи, а в качестве значений используется заглушка `Object PRESENT`). Также гарантирует сортировку и уникальность элементов.

### 21. Hierarchy of collections. Tell us what it looks like and name the implementations
Интерфейс **`Map`** стоит отдельно, он не наследуется от интерфейса `Iterable` или `Collection`.

```
                         Iterable
                            │
                        Collection
         ┌──────────────────┼─────────────────┐
       List                Set              Queue
    ┌────┴─────┐         ┌──┴──────┐          │
 ArrayList  LinkedList HashSet TreeSet  PriorityQueue
                         │
                      LinkedHashSet
```
* **Map Hierarchy**: `Map` -> `HashMap`, `Hashtable`, `LinkedHashMap`, `SortedMap` -> `TreeMap`.

### 22. Exception hierarchy. Checked and Unchecked exceptions
Все исключения наследуются от класса **`Throwable`**.

```
                           Throwable
                     ┌─────────┴─────────┐
                   Error             Exception
                               ┌─────────┴─────────┐
                       Checked Exceptions     RuntimeException (Unchecked)
                      (IOException, etc.)     (NullPointerException, etc.)
```
* **Checked Exceptions (Проверяемые)**: Наследуются от `Exception` (но не от `RuntimeException`). Компилятор заставляет нас обрабатывать их в блоке `try-catch` или объявлять в сигнатуре метода (`throws`). Представляют внешние предсказуемые ошибки (например, файл не найден `FileNotFoundException`).
* **Unchecked Exceptions (Непроверяемые)**: Наследуются от `RuntimeException`. Не требуют обязательной обработки. Представляют ошибки логики программирования (выход за границы массива `ArrayIndexOutOfBoundsException`, деление на ноль, обращение к `null`).
* **Error**: Наследуются от `Error`. Серьезные системные проблемы JVM (нехватка памяти `OutOfMemoryError`, переполнение стека `StackOverflowError`). Приложение не должно пытаться их обрабатывать.

### 23. What are wrapper classes and why are they needed? (Классы-обертки)
Для каждого примитивного типа есть соответствующий ссылочный класс-обертка: `int -> Integer`, `char -> Character`, `double -> Double` и т.д.
* **Зачем нужны**:
  1. Чтобы использовать примитивы в **Коллекциях** и дженериках (нельзя написать `List<int>`, только `List<Integer>`).
  2. Предоставляют полезные методы утилит (парсинг строк `Integer.parseInt("123")`, получение максимальных/минимальных границ).
  3. Могут принимать значение `null` (полезно при работе с базами данных, когда поле может отсутствовать).
  * Переход между примитивом и оберткой выполняется автоматически: **Autoboxing** (автоупаковка) и **Unboxing** (автораспаковка).

---

### 24. Immutable objects. Examples in Java. How to create them? (Неизменяемые объекты)
**Immutable Object** — это объект, состояние которого нельзя изменить после его создания.
* *Примеры*: Класс `String`, классы-обертки примитивов, `BigDecimal`, `LocalDate`, новые классы-записи `record` (появились в Java 14).
* **Как создать кастомный Immutable класс:**
  1. Сделать класс **`final`**, чтобы исключить наследование и переопределение.
  2. Сделать все поля **`private final`**.
  3. Инициализировать все поля строго в конструкторе.
  4. Не создавать сеттеры.
  5. Если поля являются ссылками на изменяемые объекты (например, `List` или `Date`), в конструкторе и геттерах нужно делать **Глубокое копирование (Defensive Copying)**, чтобы пользователи класса не могли изменить внутреннее состояние объекта извне.

---

### 25. What is serialization in Java? What do you need to do to serialize them? What is serialVersionUID?
* **Сериализация** — процесс преобразования состояния объекта в последовательность байт (для сохранения в файл, БД или передачи по сети). **Десериализация** — обратный процесс восстановления объекта из байт.
* **Что нужно сделать**: Класс должен реализовывать маркерный интерфейс **`Serializable`**.
* **`serialVersionUID`** — это уникальный идентификатор версии сериализованного класса. Компилятор использует его при десериализации, чтобы убедиться, что класс, в который загружаются байты, соответствует классу, из которого они были записаны. Если `serialVersionUID` не совпадают, выбросится `InvalidClassException`. Лучшая практика — объявлять его явно: `private static final long serialVersionUID = 1L;`.

---

### 26. What is the volatile keyword for?
Ключевое слово `volatile` применяется к переменным и решает две важные проблемы многопоточности:
1. **Видимость (Visibility)**: Изменения переменной, сделанные одним потоком, немедленно становятся видны всем остальным потокам. Потоки не кэшируют значение `volatile`-переменной в своих локальных регистрах или кэшах ядер CPU, а всегда читают и пишут её напрямую в общую оперативную память (RAM).
2. **Запрет переупорядочивания команд (Instruction Reordering)**: Компилятор и CPU в целях оптимизации могут менять порядок выполнения инструкций. `volatile` запрещает это, выстраивая барьер памяти (Memory Barrier).
* *Важно: `volatile` не гарантирует атомарность операции (например, инкремент `count++` все равно не будет потокобезопасным).*

---

### 27. Is an array an object or a primitive? (Массив — это объект или примитив?)
Массив в Java — это всегда **ссылочный тип данных (Объект)**, даже если это массив примитивов (например, `int[]`). Он выделяется в куче (Heap), наследуется от класса `Object` и у него можно вызвать методы (например, `.toString()`, `.hashCode()`) и обратиться к полю `.length`.

---

### 28. Thread.sleep vs Thread.yield разница
* **`Thread.sleep(millis)`**: Текущий поток приостанавливает свое выполнение на указанное время и переходит в состояние `TIMED_WAITING`. При этом поток **НЕ освобождает занятые им блокировки (мониторы)**.
* **`Thread.yield()`**: Это "подсказка" планировщику потоков операционной системы о том, что текущий поток готов уступить процессорное время другим потокам такого же приоритета. Поток переходит в состояние `RUNNABLE`, но планировщик может проигнорировать эту подсказку и сразу же продолжить выполнение текущего потока. Мониторы также не освобождаются.

---

### 29. How do wait, notify, notifyAll work?
Это методы класса `Object`, используемые для межпоточного взаимодействия (Inter-Thread Communication).
* Могут вызываться **только внутри синхронизированного контекста** (блока или метода `synchronized`), иначе выбросится `IllegalMonitorStateException`.
* **`wait()`**: Текущий поток освобождает монитор (блокировку) объекта и засыпает (состояние `WAITING`), пока другой поток не вызовет на этом же объекте `notify()` или `notifyAll()`.
* **`notify()`**: Пробуждает один случайный поток, который ранее заснул на мониторе этого объекта. Пробужденный поток сможет продолжить работу только после того, как текущий поток освободит монитор.
* **`notifyAll()`**: Пробуждает все потоки, ожидающие на мониторе объекта. Это более безопасный выбор во избежание дедлоков и зависаний.

---

### 30. How does the Thread.join() method work?
Метод `join()` заставляет вызывающий поток дождаться завершения потока, на котором этот метод был вызван.
* *Пример*: Если в потоке `main` мы вызываем `thread1.join()`, то поток `main` приостановит выполнение и будет ждать, пока `thread1` полностью не завершит работу (состояние `TERMINATED`).
* Под капотом `join()` реализован как цикл с вызовом `wait()`, пока поток `isAlive()` возвращает `true`.

---

### 31. What is AtomicInteger and how does it work?
**`AtomicInteger`** — класс из пакета `java.util.concurrent.atomic`, предоставляющий потокобезопасные атомарные операции над целым числом без использования тяжелых блокировок (`synchronized`).
* **Как работает**: Основан на низкоуровневой аппаратной поддержке процессора — операции **CAS (Compare-And-Swap / Сравнение с обменом)**.
* Алгоритм CAS за один такт процессора делает следующее: он берет текущее значение переменной, сверяет его с ожидаемым старым значением, и если они совпадают, записывает новое значение. Если значение изменилось другим потоком, операция повторяется в цикле до успешного выполнения.

---

### 32. Why is the transient keyword needed?
Ключевое слово `transient` применяется к полям класса. Оно указывает компилятору, что данное поле **не должно участвовать в процессе сериализации**. При сериализации объекта значение `transient`-поля будет проигнорировано, а при десериализации оно примет значение по умолчанию (например, `null` для ссылок или `0` для чисел). Полезно для скрытия паролей или кэшированных расчетных полей.

---

### 33. What are deadlock and livelock?
* **Deadlock (Взаимная блокировка)**: Ситуация, при которой два или более потока бесконечно ожидают освобождения ресурсов, заблокированных друг другом. Потоки полностью зависают.
  * *Пример*: Поток 1 держит Монитор А и ждет Монитор Б. Поток 2 держит Монитор Б и ждет Монитор А.
* **Livelock**: Ситуация, когда потоки не заблокированы, но постоянно меняют свое состояние в ответ на действия друг друга без совершения реальной полезной работы. Аналогия из жизни: два вежливых человека пытаются разойтись в узком коридоре, одновременно шагая в одну и ту же сторону, бесконечно преграждая друг другу путь.

---

### 34. Methods for synchronizing access to shared resources (Синхронизация потоков)
1. **`synchronized` (методы и блоки)**:
   * *Плюсы*: Простота использования, автоматическое освобождение монитора при выходе из блока (даже при исключении).
   * *Минусы*: Нельзя настроить таймаут ожидания блокировки, нельзя прервать поток во время ожидания, блокировка только эксклюзивная.
2. **Интерфейс `Lock` (`ReentrantLock`)**:
   * *Плюсы*: Возможность попытки захвата блокировки с таймаутом (`tryLock()`), возможность прерывания ожидания, поддержка справедливой очереди (fairness).
   * *Минусы*: Нужно обязательно освобождать в блоке `finally` вручную (`lock.unlock()`), иначе можно заблокировать приложение навсегда.
3. **`ReadWriteLock` (`ReentrantReadWriteLock`)**:
   * Разделяет блокировку на чтение (одновременно могут читать много потоков) и запись (писать может только один). Очень эффективен при редких записях и частом чтении.
4. **Семафоры (`Semaphore`), Барьеры (`CyclicBarrier`), Защелки (`CountDownLatch`)**:
   * Специальные высокоуровневые синхронизаторы из пакета `JUC`.

---

### 35. What is the synchronized keyword used for and what are its features?
Используется для защиты критических секций кода от одновременного изменения несколькими потоками (обеспечивает взаимное исключение — Mutual Exclusion).
* **Монитор**: Блокировка всегда происходит на определенном объекте — **Мониторе**.
  * Для нестатического синхронизированного метода монитором выступает сам объект (`this`).
  * Для статического синхронизированного метода монитором выступает объект класса (`MyClass.class`).
  * Для синхронизированного блока монитор указывается явно в скобках: `synchronized(lockObj)`.
* **Свойства**:
  * **Реентерабельность (Reentrancy)**: Если поток уже владеет монитором данного объекта, он может беспрепятственно входить в другие синхронизированные методы этого же объекта, не блокируя сам себя.

---

# Блок 2. SQL & Базы данных (на примере PostgreSQL/MS SQL)

### 1. Types of JOIN. Name and tell how they differ (Типы JOIN)
Используются для объединения строк из двух таблиц на основе общего условия:
1. **INNER JOIN** — возвращает только те строки, которые имеют совпадения в обеих таблицах.
2. **LEFT (OUTER) JOIN** — возвращает все строки из левой таблицы и совпадающие строки из правой. Если совпадений нет, для правой таблицы подставляются значения `NULL`.
3. **RIGHT (OUTER) JOIN** — возвращает все строки из правой таблицы и совпадающие из левой.
4. **FULL (OUTER) JOIN** — возвращает все строки из обеих таблиц, объединяя LEFT и RIGHT JOIN. При отсутствии совпадений подставляет `NULL`.
5. **CROSS JOIN** — декартово произведение таблиц (каждая строка первой таблицы объединяется с каждой строкой второй таблицы).

---

### 2. HAVING and WHERE distinctions
* **`WHERE`**: Фильтрует строки **до того**, как будет выполнена группировка (`GROUP BY`) и вычислены агрегатные функции. В `WHERE` нельзя использовать агрегатные функции (такие как `SUM`, `AVG`, `COUNT`).
* **`HAVING`**: Фильтрует группы строк **после того**, как выполнена группировка `GROUP BY`. Используется в связке с агрегатными функциями.
  * *Пример*: `SELECT department, COUNT(*) FROM employees WHERE salary > 50000 GROUP BY department HAVING COUNT(*) > 5;`.

---

### 3. What is a primary key in SQL and why is it important? (Первичный ключ)
**Primary Key (PK)** — поле или набор полей, уникально идентифицирующих каждую запись в таблице.
* **Свойства**: Значения должны быть строго уникальными и не могут быть `NULL`. На таблице может быть только один первичный ключ.
* **Зачем нужен**: Обеспечивает целостность данных (Entity Integrity), исключает дублирование строк и автоматически создает на таблице быстрый уникальный индекс (кластеризованный индекс в MS SQL).

---

### 4. What is a foreign key and how is it used to establish relationships? (Внешний ключ)
**Foreign Key (FK)** — поле или набор полей в одной таблице, которое ссылается на первичный ключ в другой таблице.
* **Зачем нужен**: Обеспечивает ссылочную целостность данных (Referential Integrity). База данных не позволит записать в поле FK значение, которого нет в таблице-источнике PK, защищая от появления «сиротских» или некорректных записей.

---

### 5. How to build a many-to-many connection? (Связь многие-ко-многим)
Связь "многие-ко-многим" (Many-to-Many) реализуется через **промежуточную (связующую) таблицу** (Join Table / Junction Table), содержащую два внешних ключа (Foreign Keys), ссылающихся на первичные ключи обеих связываемых таблиц. Комбинация этих двух FK обычно объявляется составным первичным ключом промежуточной таблицы.

---

### 6. What is the difference between DELETE and TRUNCATE?
* **`DELETE`**:
  * Является DML-операцией (Data Manipulation Language).
  * Удаляет строки по одной, при этом для каждой строки записывает операцию в транзакционный лог. Можно использовать условие `WHERE` для выборочного удаления.
  * Работает медленнее, но поддерживает безопасный откат (`ROLLBACK`) и вызывает триггеры удаления.
* **`TRUNCATE`**:
  * Является DDL-операцией (Data Definition Language).
  * Мгновенно очищает всю таблицу целиком, освобождая занимаемые страницы памяти на диске. Нельзя использовать `WHERE`.
  * Не записывает удаление каждой строки в лог (только факт освобождения страниц), не вызывает триггеры, работает максимально быстро. Сбрасывает автоинкрементные счетчики (IDENTITY/SEQUENCE).

---

### 7. What is normalization? Name the number of forms of normalization
**Нормализация** — процесс проектирования структуры базы данных с целью минимизации избыточности данных, устранения аномалий вставки, обновления и удаления.
Всего существует около 6 нормальных форм, но на практике базы проектируют до **Третьей нормальной формы (3NF)**:
1. **1NF (Первая нормальная форма)**: Все ячейки таблиц должны содержать атомарные (неделимые) значения, и не должно быть повторяющихся групп полей или списков.
2. **2NF (Вторая нормальная форма)**: Таблица находится в 1NF, и все неключевые поля полностью зависят от всего первичного ключа целиком (актуально при составном первичном ключе).
3. **3NF (Третья нормальная форма)**: Таблица находится в 2NF, и ни одно неключевое поле не зависит транзитивно от другого неключевого поля (все поля должны зависеть только от первичного ключа напрямую).

---

### 8. What is a transaction and why is it needed?
**Транзакция** — это неделимая логическая единица работы с базой данных, состоящая из одного или нескольких SQL-запросов, которая либо выполняется полностью и успешно (**COMMIT**), либо не выполняется вовсе (**ROLLBACK**).
* **Зачем нужна**: Гарантирует целостность и согласованность данных в системе даже при аппаратных сбоях, ошибках в коде или параллельных запросах сотен пользователей (например, перевод денег со счета на счет требует списания с одной таблицы и зачисления на другую строго в одной транзакции).

---

### 9. ACID. Name the principles and levels of transaction isolation
**ACID** — четыре золотых требования к транзакциям:
1. **Atomicity (Атомарность)**: "Всё или ничего". Транзакция будет либо полностью зафиксирована, либо полностью отменена.
2. **Consistency (Согласованность)**: Транзакция переводит базу из одного валидного состояния в другое, не нарушая все правила и ограничения (constraints) схемы данных.
3. **Isolation (Изоляция)**: Параллельно выполняющиеся транзакции не должны влиять на результаты друг друга.
4. **Durability (Долговечность)**: Если транзакция закоммичена, её результаты надежно сохранены на диске и не сотрутся при внезапном отключении электричества.

**Уровни изоляции транзакций (от самого слабого к сильному):**
1. **Read Uncommitted (Чтение незафиксированных данных)**: Возможна проблема **Грязного чтения (Dirty Read)** — транзакция видит изменения, которые еще не закоммичены другой транзакцией.
2. **Read Committed (Чтение зафиксированных данных)**: (Дефолтный во многих СУБД, включая Postgres). Решает грязное чтение. Возникает проблема **Неповторяющегося чтения (Non-repeatable Read)** — при повторном чтении одной и той же строки внутри транзакции данные могут измениться из-за коммита в параллельном потоке.
3. **Repeatable Read (Повторяемость чтения)**: Решает проблему неповторяющегося чтения. Возникает проблема **Фантомного чтения (Phantom Read)** — повторный запрос выборки строк по диапазону условий возвращает новые строки ("фантомы"), добавленные параллельной транзакцией.
4. **Serializable (Сериализуемый)**: Полная имитация последовательного выполнения транзакций. Исключает все аномалии, но кардинально снижает производительность из-за тотальных блокировок таблиц.

---

### 10. Main types of indexes and how they work (Индексы)
Индексы нужны для ускорения поиска строк в таблицах. Без индексов СУБД делает полный обход таблицы (**Full Table Scan** — $O(N)$).
* **B-Tree (Сбалансированное дерево)**: Самый популярный тип индекса по умолчанию. Строит древовидную структуру данных. Позволяет находить элементы, искать диапазоны и сортировать данные за время $O(\log N)$.
* **Hash Index**: Строит хэш-таблицу. Идеален для точечного поиска "равно" (`=`), но абсолютно бесполезен для поиска диапазонов (`>`, `<`) или сортировки.
* **Кластеризованный индекс (в MS SQL)**: Физически перестраивает порядок хранения строк в самой таблице на диске в соответствии с ключом индекса. На таблице может быть только один.
* **Некластеризованный индекс**: Хранит только упорядоченные ключи и физический указатель (ссылку) на реальную строку в таблице. На таблице может быть много таких индексов.

---

### 11. What is a query execution plan and how to view it? (План выполнения запроса)
**План выполнения (Execution Plan)** — это детальное дерево шагов и алгоритмов, которые оптимизатор СУБД планирует предпринять для выполнения SQL-запроса (какие индексы использовать, как объединять таблицы — nested loop, hash join, делать ли сканирование таблицы).
* **Как посмотреть**: В начале SQL-запроса нужно написать ключевое слово **`EXPLAIN`** (для подробного анализа в Postgres — **`EXPLAIN ANALYZE`**, который реально выполнит запрос и покажет точное время каждого шага). В MS SQL для этого используют графический интерфейс SSMS.

---

# Блок 3. Spring Framework & Spring Boot

### 1. Bean lifecycle (Жизненный цикл бина в Spring)
Жизненный цикл бина управляется контейнером IoC:
1. **Сканирование и парсинг определений (BeanDefinition)**.
2. **Инстанцирование (Instantiate)**: Создание объекта бина (вызов конструктора).
3. **Внедрение зависимостей (Populate Properties)**: Внедрение зависимостей через сеттеры или поля.
4. **Оповещение Aware-интерфейсов** (`BeanNameAware`, `BeanFactoryAware`, `ApplicationContextAware` и др. — бин узнает свои имена и контекст).
5. **Пре-инициализация через BeanPostProcessors** (вызывается метод `postProcessBeforeInitialization()`).
6. **Инициализация**:
   * Вызов метода, помеченного аннотацией **`@PostConstruct`**.
   * Вызов метода `afterPropertiesSet()` интерфейса `InitializingBean`.
   * Вызов кастомного `init-method`.
7. **Пост-инициализация через BeanPostProcessors** (вызывается метод `postProcessAfterInitialization()`, именно здесь чаще всего создаются **Прокси** для бинов). Бин готов к использованию.
8. **Уничтожение (Destroy)**: При закрытии контекста:
   * Вызов метода с аннотацией **`@PreDestroy`**.
   * Вызов метода `destroy()` интерфейса `DisposableBean`.
   * Вызов кастомного `destroy-method`.

---

### 2. Methods for declaring beans. List and name pros and cons
1. **Аннотации над классами (`@Component`, `@Service`, `@Repository`, `@Controller`)**:
   * *Плюсы*: Быстрая декларация, используется автосканирование (`@ComponentScan`), минимум шаблонного кода.
   * *Минусы*: Нельзя объявить бином класс из сторонней закрытой библиотеки (так как мы не можем добавить аннотацию в чужой `.class`).
2. **Java-конфигурация (Класс `@Configuration` и методы `@Bean`)**:
   * *Плюсы*: Полный контроль над созданием объекта, можно гибко настраивать логику создания сторонних классов, передавать параметры.
   * *Минусы*: Нужно писать много конфигурационного кода вручную.
3. **XML-конфигурация (устарела)**:
   * *Плюсы*: Все бины описаны в одном файле без изменения исходного кода.
   * *Минусы*: Очень громоздкий XML-код, легко допустить опечатку, нет проверки типов на этапе компиляции.

---

### 3. Bean scopes. Name and tell about their lifecycle (Области видимости бинов)
1. **`singleton` (по умолчанию)**: Создается ровно **один экземпляр** бина на весь IoC-контейнер Spring. Живет всё время работы приложения.
2. **`prototype`**: Новый экземпляр бина создается **при каждом запросе** из контекста (через `getBean()` или при инжекте). *Важно: Spring не отслеживает дальнейший жизненный цикл Prototype-бинов и не вызывает у них деструкторы (`@PreDestroy`), очистку памяти делает GC.*

*Дополнительные области видимости (доступны только в Web-контексте Spring MVC):*
3. **`request`**: Один экземпляр на каждый входящий HTTP-запрос.
4. **`session`**: Один экземпляр на каждую HTTP-сессию пользователя.
5. **`application`**: Один экземпляр на весь жизненный цикл `ServletContext`.
6. **`websocket`**: Один экземпляр на жизненный цикл WebSocket-соединения.

---

### 4. Tools for creating proxies. Differences between Dynamic Proxy and CGLib (Как устроен Proxy?)
Spring активно использует паттерн Прокси для реализации AOP (Aspect Oriented Programming), обработки транзакций `@Transactional` и безопасности. Для создания прокси используются два механизма:
* **JDK Dynamic Proxy**:
  * Входит в состав стандартной Java API.
  * Работает **только если целевой класс реализует хотя бы один интерфейс**. Прокси-класс создается путем динамической реализации этого интерфейса.
* **CGLib (Code Generation Library)**:
  * Сторонняя библиотека, поставляемая со Spring.
  * Создает прокси путем **динамического наследования от целевого класса** (генерация байт-кода на лету). Не требует наличия интерфейсов у класса.
  * *Ограничение*: Не может создать прокси для `final` классов или методов, так как от них нельзя унаследоваться. С версии Spring Boot 2.x CGLib используется по умолчанию для всех бинов.

---

### 5. Spring MVC vs Spring Boot. Differences
* **Spring MVC**: Это веб-фреймворк из экосистемы Spring, построенный вокруг сервлета `DispatcherServlet`. Он реализует паттерн Model-View-Controller. Требует ручной детальной настройки XML или Java-конфигов, ручного подключения сервера приложений (например, Tomcat) и настройки всех зависимостей в pom.xml.
* **Spring Boot**: Это инструмент-"надстройка" над всей экосистемой Spring. Его цель — ускорить и упростить запуск приложений за счет:
  1. **Opinionated Defaults**: Концепция "соглашения выше конфигурации" (Convention over Configuration).
  2. **Starters**: Удобные наборы зависимостей (например, `spring-boot-starter-web`).
  3. **Auto-configuration**: Автоматическая настройка бинов на основе того, какие библиотеки лежат в `classpath`.
  4. **Embedded Server**: Встроенный сервер (Tomcat, Jetty) по умолчанию, запускающийся сразу из исполняемого `.jar`.

---

### 6. Distinguishes @Component from @Service and @Repository
Все три аннотации являются стереотипами (стереотипными аннотациями). На самом деле `@Service` и `@Repository` внутри себя помечены аннотацией `@Component`, то есть они также регистрируют бины в IoC контейнере. Но они несут разную семантическую нагрузку для фреймворка:
* **`@Component`** — базовая аннотация общего назначения для любого управляемого Spring-бина.
* **`@Service`** — указывает, что класс содержит бизнес-логику приложения. Никакой дополнительной технической магии не содержит, служит для семантического разделения слоев.
* **`@Repository`** — указывает на слой доступа к данным (DAO). Она включает встроенный механизм **автоматического перевода низкоуровневых исключений СУБД** (например, SQLExceptions) в унифицированные непроверяемые исключения Spring `DataAccessException`.

---

### 7. How to perform a native database query when using Spring Data JPA?
В интерфейсе репозитория `Repository` над методом нужно написать аннотацию **`@Query`**, передать туда чистый SQL-запрос и обязательно установить флаг **`nativeQuery = true`**:
```java
@Query(value = "SELECT * FROM users WHERE status = :status", nativeQuery = true)
List<UserEntity> findAllByStatusNative(@Param("status") String status);
```

### 8. How does @Transactional work in Spring? (Как устроена транзакционность?)
* **Как работает под капотом**: Spring оборачивает наш бин в **Прокси-класс** (через CGLib или JDK Proxy). Когда вызывается метод, помеченный `@Transactional`, прокси-класс перехватывает вызов, открывает транзакцию в БД с помощью `PlatformTransactionManager`, передает управление оригинальному методу, и если метод завершается успешно — делает `commit`, а если выбрасывается `RuntimeException` — делает `rollback`.
* *Важно: Самовызов метода (self-invocation) из того же класса не откроет транзакцию, так как вызов пойдет в обход прокси-класса!*

**Что будет, если один `@Transactional` метод вызовет другой?**
Это настраивается с помощью параметра **`propagation`** (распространение транзакций). По умолчанию используется `REQUIRED`:
* Если у внешнего метода уже есть транзакция, внутренний метод присоединится к ней и они выполнятся в рамках одной общей транзакции. Если внутренний упадет, откатится вся цепочка.
* Если транзакции нет, Spring создаст новую.
* *Другие типы propagation*: `REQUIRES_NEW` (всегда открывает новую транзакцию, приостанавливая текущую), `NESTED`, `MANDATORY`, `NEVER`.

2. `spring-boot-starter-data-jpa` — для работы с базами данных через Hibernate и JPA.

### 10. What is DI and IoC? (Внедрение зависимостей и Инверсия управления)
* **IoC (Inversion of Control / Инверсия управления)** — архитектурный принцип проектирования, при котором управление жизненным циклом объектов и связями между ними делегируется внешней системе (в нашем случае — Spring IoC-контейнеру/ApplicationContext), а не контролируется кодом приложения вручную.
* **DI (Dependency Injection / Внедрение зависимостей)** — это конкретный паттерн проектирования, реализующий принцип IoC. Вместо того чтобы класс сам создавал свои зависимости (`new MyService()`), эти зависимости передаются ему (внедряются) извне.
  * В Spring зависимости можно внедрять тремя способами:
    1. **Через конструктор** (Constructor Injection) — *самый рекомендуемый способ*, так как позволяет делать зависимости final (immutable) и упрощает юнит-тестирование.
    2. Через сеттер (Setter Injection).
    3. Через поле с аннотацией `@Autowired` (Field Injection) — не рекомендуется, так как скрывает зависимости и усложняет тестирование без рефлексии.

# Блок 4. Docker & Docker Compose

### 1. What is the essence of Docker and what problem does it solve?
Суть Docker — предоставить изолированную, стандартизированную среду для запуска приложений в виде легковесных контейнеров.
* **Какую проблему решает**: Проблему "у меня на компьютере всё работает, а на сервере падает" ("Works on my machine"). Он упаковывает приложение вместе со всей его экосистемой (библиотеками конкретных версий, JRE, системными утилитами) в единый образ, который гарантированно одинаково запустится на любой машине, где установлен Docker (на Windows разработчика, в Linux-сервере staging или в Kubernetes в облаке).

---

### 2. Describe in general terms what should be in the .Dockerfile
В `Dockerfile` описывается сценарий пошаговой сборки образа:
1. `FROM` — базовый образ (например, `openjdk:21-slim` или `node:18-alpine`).
2. `WORKDIR` — рабочая директория внутри контейнера.
3. `COPY` / `ADD` — копирование файлов из хост-системы в образ.
4. `RUN` — выполнение команд во время сборки образа (например, сборка проекта, установка пакетов).
5. `ENV` — объявление переменных окружения.
6. `EXPOSE` — документирование порта, который слушает контейнер.
7. `USER` — переключение на non-root пользователя в целях безопасности.
8. `ENTRYPOINT` / `CMD` — команда, выполняемая при старте готового контейнера.

---

### 3. What is docker-compose and why is it needed?
**Docker Compose** — это инструмент для описания и запуска многоконтейнерных Docker-приложений. 
* **Зачем нужен**: Позволяет описать всю необходимую инфраструктуру (базу данных, кэш, очереди, само веб-приложение) в одном файле конфигурации `docker-compose.yml` в виде декларативного кода, а затем запустить всё одной простой командой `docker compose up -d` вместо написания сотен длинных команд `docker run` в терминале вручную.

---

### 4. What are layers in images and what problem do they solve?
Каждая строка-инструкция в Dockerfile создает новый неизменяемый слой образа (ReadOnly слой UnionFS).
* **Какую проблему решают**: Огромную экономию дискового пространства и времени сборки/передачи образов.
  * *Повторное использование*: Если несколько образов базируются на одном образе `ubuntu:latest`, этот базовый слой физически скачивается на диск хоста только один раз.
  * *Кэширование*: При повторной сборке Docker переиспользует кэш для тех слоев (команд), в которых ничего не изменилось, что ускоряет сборку до долей секунды.

---

### 5. What types of networks does docker-compose allow you to install? (Сети)
Docker Compose по умолчанию создает одну общую сеть типа **`bridge`** (мост) для всех сервисов, описанных в файле. Контейнеры в этой сети могут обращаться друг к другу напрямую по именам сервисов (`container_name` или имя сервиса выступает как доменное имя в локальном DNS).

**Основные типы сетей в Docker:**
1. **bridge** (по умолчанию) — изолированная сеть на хосте. Контейнеры имеют свои приватные IP и общаются через мост.
2. **host** — убирает сетевую изоляцию. Контейнер использует сетевой стек хост-машины напрямую (порты контейнера открываются прямо на хосте).
3. **none** — полное отключение сетевого интерфейса у контейнера (абсолютная изоляция).
4. **overlay** — сеть, объединяющая контейнеры на разных физических серверах (используется в Docker Swarm).

---

### 6. Case: I launched PostgreSQL in docker, but it is not available on the system via standard port 5432. Where to look and how to diagnose?
Алгоритм диагностики по шагам:
1. **Проверить, запущен ли контейнер вообще**: Запустить `docker ps`. Если контейнера нет в списке, посмотреть упавшие контейнеры через `docker ps -a`.
2. **Изучить логи контейнера**: Запустить `docker logs <container_name>` (возможно, Postgres упал на старте из-за неверного пароля или занятого порта).
3. **Проверить маппинг портов**: Посмотреть в выводе `docker ps` колонку `PORTS`. Должно быть написано `0.0.0.0:5432->5432/tcp`. Если маппинга портов `ports` нет в `docker-compose.yml` или команде запуска, порт будет доступен только внутри Docker-сети, но не снаружи на хост-системе.
4. **Проверить, не занят ли порт 5432 на хост-системе**: Возможно, локально на компьютере уже запущен физический сервер PostgreSQL, который занял порт 5432, не давая Docker замаппить его.
5. **Проверить параметры авторизации**: Убедиться, что переданы обязательные переменные окружения (`POSTGRES_PASSWORD`).

# Блок 5. Базовые инженерные знания и Web

### 1. HTTP protocol and methods (Протокол HTTP)
HTTP (HyperText Transfer Protocol) — прикладной протокол передачи данных, работающий по модели "клиент-сервер" поверх TCP.

**Популярные методы HTTP:**
* **GET** — запрос данных с сервера. Безопасный и *идемпотентный* (повторные одинаковые вызовы дают один и тот же результат и не меняют состояние системы). Не должен содержать тела.
* **POST** — отправка новых данных на сервер (обычно создание ресурса). Не является идемпотентным (два POST запроса создадут два разных ресурса).
* **PUT** — замена или обновление существующего ресурса целиком. Идемпотентен.
* **PATCH** — частичное обновление ресурса. Не гарантирует идемпотентность (хотя часто проектируется как идемпотентный).
* **DELETE** — удаление ресурса на сервере. Идемпотентен.

---

### 2. Servlet/JSP basics (Базовые концепции сервлетов)
* **Сервлет (Servlet)** — это Java-класс, управляемый веб-контейнером (например, Tomcat), который расширяет возможности сервера и способен обрабатывать входящие HTTP-запросы и генерировать ответы (обычно переопределяет методы `doGet()`, `doPost()`).
* **JSP (JavaServer Pages)** — устаревшая технология текстовых документов, позволяющая совмещать HTML-код со вставками Java-кода. Под капотом JSP при первом обращении компилируется сервером в обычный сервлет.
* **DispatcherServlet** в Spring MVC — это главный сервлет-контроллер (Front Controller), который перехватывает абсолютно все запросы к приложению и распределяет их по конкретным контроллерам (`@RestController`).

---

### 3. REST (REpresentational State Transfer)
**REST** — это архитектурный стиль взаимодействия компонентов распределенного приложения по сети, основанный на правилах:
1. **Client-Server**: Разделение ответственности интерфейса и данных.
2. **Stateless (Без состояния)**: Сервер не хранит сессионное состояние клиента. Каждый запрос должен содержать абсолютно всю информацию, необходимую для его обработки (например, JWT токен в заголовке).
3. **Cacheable**: Ответы сервера должны явно помечаться как кэшируемые или некэшируемые.
4. **Uniform Interface (Единый интерфейс)**: Использование стандартных методов HTTP, уникальных URI для ресурсов (например, `/api/v1/vacancies`), и стандартных форматов передачи данных (JSON/XML).
5. **Layered System (Слоистая система)**: Клиент не знает, общается он напрямую с сервером или через промежуточные прокси/балансировщики.

---

### 4. Дополнительные связи объектов в ООП (Association, Aggregation, Composition)
Помимо наследования и реализации, в ООП выделяют связи владения и использования:
1. **Ассоциация (Association)** — общая связь, когда один объект просто использует другой или знает о нем (класс `User` имеет ссылку на класс `Address`).
2. **Агрегация (Aggregation)** — отношение "целое-часть" (слабая связь), когда один объект входит в состав другого, но их жизненные циклы **не связаны**. Если целое уничтожается, часть продолжает жить.
   * *Пример*: Класс `Library` (Библиотека) и класс `Book` (Книга). Если библиотека закроется и сотрется, книги останутся жить сами по себе.
3. **Композиция (Composition)** — отношение "целое-часть" (жесткая связь), когда часть **не может существовать без целого**. Жизненный цикл части полностью управляется целым.
   * *Пример*: Класс `Room` (Комната) и класс `House` (Дом). Если дом снести, все комнаты внутри него уничтожатся автоматически, они не могут существовать без дома.
