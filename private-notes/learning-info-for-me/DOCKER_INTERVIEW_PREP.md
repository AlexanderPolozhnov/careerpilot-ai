## 1. Базовая теория: Виртуализация vs Контейнеризация

Тимлиды обожают начинать собеседование с фундаментального вопроса о разнице между виртуалками и контейнерами.

### 🎙️ Вопрос Тимлида: *"В чем ключевая разница между виртуальной машиной (например, VirtualBox / VMware) и контейнером Docker?"*

**💡 Твой ответ (как сказать правильно):**
> «Главное отличие заключается в **уровне абстракции** и совместном использовании ресурсов хост-системы.
>
> 1. **Виртуальные машины (ВМ)** виртуализируют **аппаратное обеспечение** (железо). Каждая ВМ запускается поверх специального слоя — **гипервизора**, и содержит внутри себя **полноценную гостевую операционную систему** (со своим ядром, драйверами, системными библиотеками). Из-за этого ВМ весят гигабайты, запускаются по несколько минут и потребляют много ресурсов.
> 2. **Контейнеры Docker** виртуализируют **операционную систему** на уровне ядра. Все контейнеры запускаются прямо на хост-машине и **разделяют между собой одно и то же ядро ОС хоста**. Docker-контейнер — это, по сути, изолированный процесс в ОС. Из-за отсутствия гостевой ОС контейнеры весят мегабайты, запускаются за секунды и практически не создают накладных расходов на производительность».

```
      ВИРТУАЛЬНЫЕ МАШИНЫ (ВМ)                  DOCKER КОНТЕЙНЕРЫ
 ┌───────────────────────────────┐          ┌───────────────────────────┐
 │  Приложение A │ Приложение B  │          │ Приложение A │Приложение B│
 ├───────────────┼───────────────┤          ├──────────────┼────────────┤
 │ Библиотеки A  │ Библиотеки B  │          │ Библиотеки A │Библиотеки B│
 ├───────────────┼───────────────┤          ├──────────────┴────────────┤
 │ Гостевая ОС A │ Гостевая ОС B │          │      Docker Engine        │
 ├───────────────┴───────────────┤          ├───────────────────────────┤
 │          Гипервизор           │          │     Ядро Хост-ОС (Linux)  │
 ├───────────────────────────────┤          ├───────────────────────────┤
 │     Физический сервер (ОС)    │          │     Физический сервер     │
 └───────────────────────────────┘          └───────────────────────────┘
```

### 🛠️ Механизмы ядра Linux под капотом Docker:
Если собеседующий спросит: *"За счет чего конкретно ядро Linux изолирует контейнеры?"*, назови эти три технологии:
1. **Namespaces (Пространства имен)** — отвечают за **изоляцию**. Они скрывают процессы друг от друга. Есть namespaces для сети (`net`), процессов (`pid`), файловой системы (`mnt`), пользователей (`user`) и хостнеймов (`uts`). Контейнер "думает", что он один в системе.
2. **Cgroups (Control Groups / Контрольные группы)** — отвечают за **ограничение ресурсов**. Они позволяют жестко лимитировать, сколько оперативной памяти (RAM), CPU, дискового I/O или сетевой полосы может потреблять конкретный контейнер.
3. **UnionFS (Union File System)** — слоистая файловая система, которая позволяет объединять разные папки в одну общую файловую систему, обеспечивая работу неизменяемых слоев образов.

## 2. Основные термины Docker

### 🎙️ Вопрос Тимлида: *"Объясните простыми словами разницу между Docker Image и Docker Container"*

**💡 Твой ответ:**
> «**Docker Image (Образ)** — это неизменяемый шаблон (чертеж), который содержит в себе всё необходимое для запуска приложения: код, среду выполнения, библиотеки, переменные окружения и конфигурационные файлы. Его можно сравнить с классом в ООП (Java class) или с установочным диском игры.
>
> **Docker Container (Контейнер)** — это запущенный, живой экземпляр образа. Это изолированный процесс в операционной системе. Его можно сравнить с объектом класса (object) в ООП или с установленной и запущенной игрой. Контейнер добавляет поверх неизменяемых слоев образа свой тонкий **записываемый слой (Read-Write Layer)**, куда сохраняются все изменения, сделанные во время его работы».

## 3. Разбор инфраструктуры в CareerPilot AI (Docker Compose)

В нашем проекте для локальной разработки и развертывания используется `docker-compose.yml`, который оркеструет несколько связанных сервисов: PostgreSQL, Redis, MinIO (S3 хранилище) и Ollama (для локального AI).

### 🎙️ Вопрос Тимлида: *"Как устроен ваш docker-compose.yml в CareerPilot AI? Какие интересные фичи Docker Compose вы использовали?"*

**💡 Твой ответ (показывает глубокое практическое владение инструментом):**
> «В нашем проекте `docker-compose.yml` описывает полную инфраструктуру приложения: `postgres:16-alpine`, `redis:7-alpine`, `minio/minio`, `ollama/ollama`, **а также `backend` (Spring Boot) и `frontend` (React + Nginx)** — всего 6 сервисов. То есть всё приложение запускается одной командой `docker compose up`.
>
> Из продвинутых фич Docker Compose мы применили три критически важные вещи:
> 1. **Профили (Profiles)**: Тяжелые опциональные сервисы (Ollama, MinIO) вынесены в отдельные профили: `profiles: [ "ai" ]` и `profiles: [ "storage" ]`. Команда `docker compose up -d` запускает основной стек (PostgreSQL + Redis + backend + frontend), а тяжелые компоненты запускаются только по явному требованию: `docker compose --profile ai up -d`.
> 2. **Проверки здоровья (Healthchecks)**: Для PostgreSQL используется утилита `pg_isready`, для Redis — `redis-cli ping`. Параметры хельсчека PostgreSQL берутся из переменных окружения (`${DB_USER:-postgres}`), а не хардкодятся.
> 3. **Управление порядком запуска (`depends_on` с условиями)**: Контейнер `backend` начинает стартовать только после успешного прохождения Postgres и Redis своих хельсчеков (`condition: service_healthy`). Это исключает ошибки подключения аппликации при первом запуске».

### Сниппет нашего `docker-compose.yml` для иллюстрации:
```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: careerpilot-postgres
    restart: unless-stopped
    environment:
      POSTGRES_DB: ${DB_NAME:-careerpilot_ai}
      POSTGRES_USER: ${DB_USER:-postgres}
      POSTGRES_PASSWORD: ${DB_PASSWORD:-postgres}
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: [ "CMD-SHELL", "pg_isready -U ${DB_USER:-postgres} -d ${DB_NAME:-careerpilot_ai}" ]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    container_name: careerpilot-redis
    restart: unless-stopped
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    healthcheck:
      test: [ "CMD", "redis-cli", "ping" ]
      interval: 10s
      timeout: 5s
      retries: 5

  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    container_name: careerpilot-backend
    restart: unless-stopped
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    environment:
      DB_HOST: postgres
      DB_NAME: ${DB_NAME:-careerpilot_ai}
      JWT_SECRET: ${JWT_SECRET}
      REDIS_HOST: redis
      # ... остальные переменные из .env
    ports:
      - "8080:8080"

  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    container_name: careerpilot-frontend
    restart: unless-stopped
    depends_on:
      - backend
    ports:
      - "80:80"
```
> **Что сказать про `backend` и `frontend` сервисы:**
> Мы не только описываем инфраструктурные сервисы, но и само приложение. Фронтенд собирается через Multi-stage сборку в своем Dockerfile и раздаётся на **порту 80 через Nginx**. Бэкенд стартует **только после** гарантированной готовности PostgreSQL и Redis.

## 4. Хранение данных: Bind Mounts vs Volumes

### 🎙️ Вопрос Тимлида: *"Контейнеры эфемерны — при удалении контейнера все данные внутри него стираются. Как вы сохраняете данные (например, таблицы PostgreSQL) между перезапусками?"*

**💡 Твой ответ:**
> «Для персистентности данных в Docker используются два основных механизма:
>
> 1. **Named Volumes (Именованные тома / Олицетворение Docker)**:
>    * *Как работает*: Docker сам создает и управляет специальной директорией на хост-машине (в Linux по умолчанию в `/var/lib/docker/volumes/`). Мы просто связываем эту директорию с внутренней папкой контейнера (например, `- postgres_data:/var/lib/postgresql/data`).
>    * *Когда использовать*: Для хранения баз данных (PostgreSQL, Redis), медиафайлов. Это самый производительный и безопасный способ, изолированный от случайного удаления пользователем хоста.
> 2. **Bind Mounts (Связанные папки)**:
>    * *Как работает*: Мы жестко связываем конкретную папку на жестком диске хоста (например, `/home/user/project/logs`) с папкой внутри контейнера.
>    * *Когда использовать*: Для прокидывания конфигурационных файлов (например, `application.yaml`), SSL-сертификатов или для маппинга исходного кода во время локальной разработки фронтенда (чтобы работал Hot Reload)».

## 5. Продвинутые вопросы для Middle/Senior (Безопасность и оптимизация)

Вот те самые вопросы, по которым тимлид отличает "теоретика по видео-курсам" от опытного инженера.

### 🔥 Тонкость №1: Многоэтапная сборка (Multi-stage Builds)
* **Тимлид спрашивает:** *"Что такое Multi-stage сборка в Dockerfile, зачем она нужна в Java/React проектах?"*
* **Ты отвечаешь:**
  > «**Multi-stage build** — это подход, при котором внутри одного Dockerfile мы используем несколько инструкций `FROM` для разделения процесса сборки приложения и его финального запуска.
  > 
  > **Зачем это нужно для Spring Boot:**
  > Чтобы собрать Java-приложение, нам нужен тяжелый образ **JDK (Java Development Kit)**, содержащий компилятор, Maven/Gradle и кучу утилит сборки (весит ~500-800 МБ). Но чтобы просто запустить готовый `.jar` файл, нам нужен легкий образ **JRE (Java Runtime Environment)** или минимальный дистрибутив Linux (весит ~100-150 МБ).
  >
  > **Реальный Dockerfile бэкенда в CareerPilot AI:**
  > ```dockerfile
  > # Стейдж 1: Сборка через Maven Wrapper + JDK
  > FROM eclipse-temurin:21-jdk-alpine AS builder
  > WORKDIR /app
  > COPY .mvn/ .mvn/
  > COPY mvnw pom.xml ./
  > RUN chmod +x mvnw
  > # Предзагрузка зависимостей в отдельный слой (кэш не сбрасывается при изменении исходников)
  > RUN ./mvnw dependency:go-offline -B
  > COPY src/ src/
  > RUN ./mvnw package -DskipTests -B
  > 
  > # Стейдж 2: Легковесный JRE для запуска
  > FROM eclipse-temurin:21-jre-alpine
  > WORKDIR /app
  > # Копируем ТОЛЬКО скомпилированный JAR из предыдущего стейджа
  > COPY --from=builder /app/target/*.jar app.jar
  > EXPOSE 8080
  > ENTRYPOINT ["java", "-jar", "app.jar"]
  > ```
  > **Результат:** ~150 МБ вместо ~800 МБ полного JDK. Ключевая оптимизация: `./mvnw dependency:go-offline` копируется до исходников, так что при повторной сборке его слой берется из кэша (Maven не перезакачивает зависимости).
  >
  > **Dockerfile фронтенда (React + Nginx, тоже Multi-stage):**
  > ```dockerfile
  > FROM node:20-alpine AS builder
  > WORKDIR /app
  > RUN corepack enable && corepack prepare pnpm@9 --activate
  > COPY package.json pnpm-lock.yaml ./
  > RUN pnpm install --frozen-lockfile
  > COPY . .
  > RUN pnpm run build
  >
  > FROM nginx:alpine
  > COPY --from=builder /app/dist /usr/share/nginx/html
  > COPY nginx.conf /etc/nginx/conf.d/default.conf
  > EXPOSE 80
  > CMD ["nginx", "-g", "daemon off;"]
  > ```
  > Фронтенд собирается через pnpm (активируется через Corepack), в продакшен — легковесный `nginx:alpine` с готовым `dist/`».

### 🔥 Тонкость №2: Кэширование слоев в Docker (Оптимизация Dockerfile)
* **Тимлид спрашивает:** *"Как устроен кэш в Docker и как правильно упорядочивать инструкции в Dockerfile для ускорения сборки?"*
* **Ты отвечаешь:**
  > «Каждая инструкция в Dockerfile (`RUN`, `COPY`, `ADD`) создает новый неизменяемый слой образа. Docker кэширует каждый слой.
  > При повторной сборке Docker идет сверху вниз и проверяет: если файлы, используемые в инструкции, или сама команда не изменились, он берет готовый слой из кэша. Но **как только какой-то слой изменился, этот кэш и ВСЕ последующие слои ниже по Dockerfile полностью инвалидируются** и собираются заново.
  >
  > **Главное правило оптимизации**: Располагать самые редко меняющиеся вещи (зависимости, настройки) в самом верху, а часто меняющиеся (исходный код, верстка) — в самом низу.
  > 
  > *Пример плохой практики:* Копировать весь код проекта, а потом запускать установку библиотек (`npm install` или `mvn dependency`). Изменение одной точки в коде заставит Docker часами перевыкачивать библиотеки.
  > *Пример хорошей практики:* Сначала скопировать только `package.json` (или `pom.xml`), запустить `npm install` (или `mvn dependency:go-offline`), и только затем скопировать исходный код».

### 🔥 Тонкость №3: Безопасность — запуск от Non-Root пользователя
> **Примечание по проекту:** В текущем `Dockerfile` бэкенда non-root пользователь пока не настроен, приложение запускается от root. Это — известный технический долг (security hardening), который важен для продакшн-енва и является следующим шагом улучшения.

* **Тимлид спрашивает:** *"Почему запускать приложение внутри контейнера под пользователем root — это плохая практика, и как это исправить?"*
* **Ты отвечаешь:**
  > «По умолчанию процессы в Docker-контейнере запускаются от имени пользователя `root` (UID 0). Пользователь `root` внутри контейнера имеет те же права суперпользователя, что и `root` на хост-машине (так как ядро ОС у них общее).
  > Если злоумышленник сможет взломать наше Java-приложение (например, через уязвимость удаленного выполнения кода вроде Log4Shell) и найдет способ выйти за пределы изоляции контейнера (**Container Breakout**), он мгновенно получит полный контроль над всем физическим сервером хоста с правами root.
  >
  > **Как это исправить**: Всегда создавать в Dockerfile отдельного системного не-привилегированного пользователя и переключаться на него перед запуском приложения:»
  > ```dockerfile
  > FROM eclipse-temurin:21-jre-alpine
  > WORKDIR /app
  > # Создаем системную группу и пользователя careerpilot
  > RUN addgroup -S careerpilot && adduser -S careerpilot -G careerpilot
  > COPY --from=builder /app/target/careerpilot.jar app.jar
  > # Меняем владельца файлов на созданного пользователя
  > RUN chown -R careerpilot:careerpilot /app
  > # Переключаемся на non-root пользователя
  > USER careerpilot
  > ENTRYPOINT ["java", "-jar", "app.jar"]
  > ```

### 🔥 Тонкость №4: Разница между CMD и ENTRYPOINT
* **Тимлид спрашивает:** *"В чем разница между инструкциями `CMD` и `ENTRYPOINT` в Dockerfile?"*
* **Ты отвечаешь:**
  > «Обе инструкции задают команду, которая будет выполнена при старте контейнера, но работают по-разному:
  > - **`ENTRYPOINT`** — задает **основной исполняемый файл** (команду), которая всегда запускается при старте контейнера. Её сложно случайно переопределить при запуске контейнера из терминала.
  > - **`CMD`** — задает **аргументы по умолчанию** для `ENTRYPOINT`. Если `ENTRYPOINT` не указан, `CMD` работает как самостоятельная команда. Но ключевое отличие в том, что `CMD` очень легко переопределить: любые аргументы, переданные в конце команды `docker run <image> <args>`, полностью заменят то, что написано в `CMD`.
  >
  > **Лучшая практика совместного использования:**
  > ```dockerfile
  > ENTRYPOINT ["java", "-jar", "app.jar"]
  > CMD ["--server.port=8080"]
  > ```
  > *При старте по умолчанию запустится `java -jar app.jar --server.port=8080`. Но если мы запустим контейнер с параметром `docker run my-app --server.port=9090`, аргумент из CMD автоматически заменится на переданный пользователем*».

### 🔥 Тонкость №5: Разница между COPY и ADD
* **Тимлид спрашивает:** *"В чем разница между COPY и ADD?"*
* **Ты отвечаешь:**
  > «Обе команды копируют файлы из хост-системы внутрь образа, но `ADD` имеет две дополнительные "скрытые" функции:
  > 1. **Распаковка архивов**: Если источник в `ADD` является локальным архивом известного формата (tar, gzip, bzip2), `ADD` автоматически распакует его как папку в целевую директорию образа.
  > 2. **Загрузка по URL**: `ADD` может принимать в качестве источника удаленный URL-адрес и скачивать файл по сети во время сборки образа.
  >
  > **Лучшая практика**: Всегда использовать **`COPY`**, так как она прямолинейна, предсказуема и безопасна. Использовать `ADD` рекомендуется только тогда, когда вам действительно необходимо автоматически распаковать локальный `.tar` архив в образ».
