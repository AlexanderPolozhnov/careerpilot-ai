# Windsurf AI Workflow — Spring Boot + React CRM

> Модели: **SWE-1.6** (бесплатно) · **Kimi K2.6** (промо, бесплатно) · **GPT-5.5 Low** (квота, точечно)

---

## Общий принцип

```
ТЗ → Архитектура (GPT-5.5) → Планы/контракты (GPT-5.5) → Реализация (Kimi + SWE-1.6) → Правки (SWE-1.6)
```

GPT-5.5 тратит квоту — использовать **только на этапах планирования**, не на кодинге.  
Kimi K2.6 бесплатен по промо — использовать **максимально** пока это так.  
SWE-1.6 всегда бесплатен — **основная рабочая лошадка**.

---

## Этап 0 — Получено новое ТЗ

### Действие: прочитать, структурировать, задать уточняющие вопросы себе

Перед тем как открывать Windsurf — ответить на вопросы:
- Какие сущности? (Client, Deal, Task, User, Pipeline…)
- Какие роли? (Admin, Manager, Viewer…)
- Какие интеграции? (Email, Telegram, 1C…)
- Какой деплой? (Docker, VPS, Cloud…)

---

## Этап 1 — Архитектура проекта

**Модель: GPT-5.5 Low Thinking**  
**Режим: Plan (не Write)**

### Промт для GPT-5.5:

```
Ты senior architect. Вот ТЗ на CRM систему:
[вставить ТЗ]

Составь:
1. Список всех доменных сущностей и их связей
2. Структуру модулей Spring Boot (packages, слои: controller/service/repository/dto)
3. Структуру фронтенда React (pages, components, hooks, api, store)
4. Список REST API эндпоинтов с HTTP методами
5. Стек технологий (Spring Security, JWT, PostgreSQL, Liquibase, React Query, Zustand и тд)
6. Приоритизацию: что реализовывать в первую очередь (MVP vs nice-to-have)

Формат: структурированный Markdown
```

### Результат: сохранить как `ARCHITECTURE.md` в корне проекта

## Этап 2 — Создание файлов-контрактов

**Модель: GPT-5.5 Low Thinking**  
**Режим: Plan → потом Write для создания файлов**

### 2.1 — AGENTS.md (главный файл инструкций для всех агентов)

Промт:
```
На основе архитектуры [прикрепить ARCHITECTURE.md] создай AGENTS.md файл.
Он должен содержать:
- Описание проекта (стек, назначение)
- Правила кодинга (naming conventions, структура пакетов Java, структура компонентов React)
- Что НЕЛЬЗЯ делать (не трогать auth без явного указания, не менять схему БД без миграции и тд)
- Как создавать новые фичи (шаблон последовательности действий)
- Переменные окружения и где они хранятся
```

### 2.2 — PLAN.md (пошаговый план реализации)

Промт:
```
Составь PLAN.md — детальный план реализации CRM по спринтам.
Каждый пункт — конкретная задача с указанием:
- [ ] Задача
- Файлы которые затронет
- Зависимости (что должно быть готово до этого)

Начни с MVP: аутентификация → базовые CRUD сущностей → UI страницы → бизнес-логика
```

### 2.3 — API контракты

Промт:
```
Создай api-contracts.md с полным описанием всех REST эндпоинтов:
- URL, метод, описание
- Request body (JSON пример)
- Response body (JSON пример)  
- HTTP коды ответов
- Требуется ли авторизация

Стек: Spring Boot, JWT Bearer token
```

### 2.4 — DB схема

Промт:
```
Создай db-schema.md со схемой базы данных:
- Все таблицы с полями и типами
- Внешние ключи и связи
- Индексы
- Также создай Liquibase changelog XML для первоначальной миграции
```

## Этап 3 — Scaffolding проекта (скелет)

**Модель: Kimi K2.6**  
**Режим: Write**

Kimi лучше справляется с генерацией структуры с нуля.

### Промт для Kimi:

```
Прочитай AGENTS.md и ARCHITECTURE.md.

Создай полный скелет Spring Boot проекта:
- pom.xml со всеми зависимостями
- application.yml (с плейсхолдерами для env переменных)
- Структуру пакетов (пустые классы с правильными аннотациями)
- SecurityConfig с JWT
- Базовые entity классы для [список сущностей]
- Liquibase changelog

Не реализуй бизнес-логику — только структуру.
```

Отдельный промт для фронтенда:
```
Прочитай AGENTS.md и ARCHITECTURE.md.

Создай скелет React проекта (Vite + TypeScript):
- package.json с зависимостями (React Query, Zustand, React Router, Axios, Shadcn/ui или Ant Design)
- Структуру папок src/ (pages, components, hooks, api, store, types)
- Базовый роутинг
- Axios instance с interceptors для JWT
- Типы TypeScript для всех сущностей из api-contracts.md
```

## Этап 4 — Реализация фич (основной цикл)

### Правило выбора модели:

| Задача | Модель |
|--------|--------|
| Новый модуль/фича с нуля (Service + Controller + DTO) | **Kimi K2.6** |
| React страница/компонент с нуля | **Kimi K2.6** |
| Добавить метод в существующий сервис | **SWE-1.6** |
| Правка логики, рефакторинг | **SWE-1.6** |
| Баг в существующем коде | **SWE-1.6** |
| Сложная бизнес-логика (непонятно как реализовать) | **GPT-5.5 Low** |
| Настройка Spring Security, JWT, CORS | **GPT-5.5 Low** |

## Этап 5 — Когда GPT-5.5 оправдан

Тратить квоту только на:

- **Spring Security конфиг** — сложная тема, ошибки дорого стоят
- **JWT + refresh token логика** — много нюансов
- **Сложные SQL запросы / JPQL** — когда Kimi/SWE-1.6 делают неправильно
- **Архитектурные решения** — "как лучше реализовать X"
- **Code review** — попросить проверить критичный кусок кода

Промт для GPT-5.5 code review:
```
Проверь этот код на:
- Проблемы безопасности
- Потенциальные баги
- Соответствие Spring Boot best practices
- N+1 проблемы с БД

[вставить код]
```

## Этап 6 — Отладка и баги

**Модель: SWE-1.6**

```
Получаю ошибку:
[стектрейс или описание]

Контекст: [какой файл, что делает]
```

Если SWE-1.6 не решил за 2 попытки → переключиться на Kimi K2.6.  
Если и Kimi не решил → GPT-5.5 Low (но это редкость).

---

## Памятка — экономия квоты

- Используй **Plan режим** перед Write — Kimi/GPT-5.5 лучше планируют чем сразу пишут
- Держи **контекст сессии минимальным** — открывай только нужные файлы через @
- Не начинай новую сессию без нужды — кэш токенов экономит квоту
- После каждого спринта обновляй **PLAN.md** (вычёркивай сделанное)
- Если задача большая — **разбей на подзадачи**, по одному промту на каждую

## Быстрая шпаргалка

```
Новое ТЗ          → GPT-5.5 (архитектура + планы)

Квота кончается   → только SWE-1.6 до сброса
```
