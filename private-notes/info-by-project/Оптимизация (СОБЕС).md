# Шпаргалка для собеседования: Производительность, Многопоточность и Масштабируемость

Этот документ поможет тебе ответить на сложные архитектурные вопросы, используя примеры из **CareerPilot AI**.

---

## 1. Многопоточность и Асинхронность

### **Вопрос: Как вы обрабатываете длительные операции на бэкенде?**
**Ответ:** Используем асинхронную модель выполнения (`@Async` в Spring). 
*   **Как достигается:** Через `CompletableFuture` и кастомные пулы потоков (`ThreadPoolTaskExecutor`).
*   **Пример из проекта:** Генерация ответов ИИ. Запрос к LLM может длиться 10 секунд. Мы не блокируем поток веб-сервера (Tomcat), а отдаем `CompletableFuture`. Это позволяет серверу обрабатывать другие запросы, пока ИИ генерирует ответ.
*   **Нюанс (Senior level):** Мы используем `DelegatingSecurityContextAsyncTaskExecutor` для проброса `SecurityContext` (текущего пользователя) в асинхронные потоки, чтобы аудит и фильтры по `userId` работали корректно.

### **Вопрос: Зачем нужна событийная архитектура (EDA) внутри монолита?**
**Ответ:** Для уменьшения связанности (decoupling) и ускорения отклика.
*   **Пример из проекта:** При изменении статуса отклика (`Application`) нам нужно отправить уведомление и записать лог. Вместо вызова этих сервисов напрямую, мы публикуем `ApplicationStatusChangedEvent`. 
*   **Что дает:** Основная бизнес-логика выполняется быстро, а "тяжелые" уведомления (Email/Telegram) уходят в фоне через слушателей (`@EventListener`).

## 2. Производительность БД и Hibernate

### **Вопрос: Как оптимизировать работу с базой данных при большом количестве мелких операций?**
**Ответ:** Использование Batching (пакетная обработка).
*   **Как достигается:** Настройка `spring.jpa.properties.hibernate.jdbc.batch_size` (в проекте установлено 25).
*   **Что дает:** Hibernate объединяет несколько `INSERT` или `UPDATE` в один сетевой пакет к БД. Это радикально снижает Round Trip Time (RTT) и нагрузку на сеть.

### **Вопрос: Как вы решаете проблему N+1 в Hibernate?**
**Ответ:** Используем `@EntityGraph`.
*   **Пример из проекта:** В аналитике нам нужны данные вакансии и компании. Вместо десятков мелких запросов, мы указываем `@EntityGraph(attributePaths = {"vacancy", "vacancy.company"})`, что заставляет Spring Data JPA выполнить один эффективный `JOIN`.

## 3. Кэширование

### **Вопрос: Когда нужно использовать Redis и как вы его применяете?**
**Ответ:** Для данных, которые дорого вычислять, но они редко меняются.
*   **Пример из проекта:** Кэширование ответов ИИ. Если пользователь дважды запрашивает анализ одной и той же вакансии с тем же резюме, мы берем результат из Redis по хешу промпта.
*   **Что дает:** Экономия токенов (денег), снижение нагрузки на API провайдера и мгновенный ответ пользователю.

## 4. Масштабируемость (Highload)

### **Вопрос: Что делать, если количество пользователей вырастет в 100 раз?**
**Ответ:** Переход от вертикального к горизонтальному масштабированию.
1.  **Stateless Backend:** Наш проект уже stateless (используем JWT, а не сессии в памяти). Это позволяет запустить 10 копий бэкенда за балансировщиком (Nginx/HAProxy).
2.  **Database Scaling:** 
    *   **Read Replicas:** Направить чтение (списки вакансий) на реплики, а запись — на мастер-ноду.
    *   **Connection Pool:** Мы уже затюнили `HikariCP` (max-pool-size, idle-timeout).
3.  **Message Broker:** Если событий в EDA станет слишком много, заменим внутренние Spring Events на **Apache Kafka** или **RabbitMQ** для надежной очереди между сервисами.
4.  **Distributed Caching:** Redis уже вынесен как отдельный сервис, его легко масштабировать в Cluster mode.

## 5. Безопасность и Стабильность

### **Вопрос: Как защитить API от перегрузки (DoS/Brute-force)?**
**Ответ:** Rate Limiting.
*   **В проекте:** Реализован `RateLimit` на уровне аспектов (Bucket4j/Redis). 
*   **Что дает:** Ограничивает количество запросов в минуту для каждого пользователя, защищая бюджет (для ИИ) и ресурсы сервера.

### **Вопрос: Как мониторить распределенную систему?**
**Ответ:** Distributed Tracing. 
*   **Рекомендация:** Упомяни **OpenTelemetry** и **Micrometer Tracing**. Это позволяет видеть путь запроса от фронтенда через все асинхронные задачи до запросов в БД.
