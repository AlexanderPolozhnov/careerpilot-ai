🧠 Теория для собеседования: Архитектура нашего CD-пайплайна

Раздельный деплой (Decoupled Deployment):

Почему два сервиса Cloud Run, а не один Docker Compose? На интервью говори так: «Мы деплоим бэкенд и фронтенд как два независимых Serverless-контейнера в Cloud Run. Это позволяет им масштабироваться независимо друг от друга. Фронтенд на Nginx практически не нагружает процессор и может иметь 0-1 минимальных инстансов, в то время как бэкенд на Spring Boot масштабируется под нагрузкой отдельно».

Динамическая сборка фронтенда (Build-time Args):

Проблема: Фронтенду при сборке нужно знать точный URL бэкенда, чтобы делать API запросы. Но в Cloud Run URL бэкенда генерируется динамически только после его первого деплоя!

Наше решение: В пайплайне мы сначала собираем и деплоим бэкенд. Команда деплоя возвращает сгенерированный URL. Мы записываем его в системную переменную $GITHUB\_ENV (шаг Deploy Backend to Cloud Run). Затем при сборке фронтенда мы передаем этот URL как --build-arg VITE\_API\_BASE\_URL=${{ env.BACKEND\_URL }} в Docker-контейнер. Это классический паттерн для SPA-приложений!

Безопасность (Least Privilege Principle):

Мы не используем учетную запись владельца (Owner) для GitHub Actions. Вместо этого мы создаем выделенный сервисный аккаунт (github-cd-sa) и даем ему только три точечные роли: запись в Artifact Registry, деплой в Cloud Run и использование рантайм-аккаунта.

🧠 Концепция "Shift Left" (Сдвиг тестирования влево)

На интервью этот принцип объясняют так:



«Мы используем подход Shift Left. Чем раньше мы обнаружим ошибку (синтаксис, линтинг, сломанный тест), тем дешевле и быстрее её исправить. Идеальная цепочка выглядит так: IDE (мгновенно) -> Git Hooks (до коммита) -> CI/CD Pipeline (в облаке перед деплоем)».



Вот почему тебе по-прежнему нужны локальные проверки и скрипт verify-all.ps1:



1\. Экономия времени разработчика (Fast Feedback Loop)

Без локальных проверок: Ты делаешь коммит, пушишь его в GitHub, ждешь 5–7 минут, пока крутится пайплайн в облаке, и только тогда узнаешь, что забыл импортировать библиотеку или пропустил точку с запятой. Ты тратишь 7 минут времени впустую.

С Git Hooks / verify-all.ps1: Ошибка линтинга или сломанный юнит-тест ловятся прямо у тебя на компьютере за 5 секунд до того, как код вообще попадет в Git.

2\. Экономия бюджета облака (Compute Minutes)

В реальных компаниях минуты работы GitHub Actions стоят денег. Если разработчики будут пушить "сломанный" код и использовать облако как компилятор, компания будет тратить огромные бюджеты на бесполезные сборки. Локальные хуки гарантируют, что в облако улетает только предварительно проверенный код.

3\. Чистота истории коммитов (Git History)

Если не делать локальных проверок, твоя история коммитов в GitHub быстро превратится в бесконечную череду сообщений:

fix: try to fix build

fix: fix typo again

fix: now really fix lint

Локальные проверки позволяют пушить чистый, рабочий код с первого раза.

Как это работает в синергии:

Локально (у тебя на ПК): Ты запускаешь verify-all.ps1 или срабатывает Git Hook, проверяя локальные тесты и линтинг.

В GitHub (CI/CD): CD-пайплайн является последним рубежом защиты (Gatekeeper). Он гарантирует, что даже если кто-то обошел локальные хуки (например, запушил с флагом --no-verify), сломанный код всё равно не попадет на прод. Кроме того, CI/CD запускает тяжелые интеграционные тесты в чистом окружении (которые локально могут не запускаться из-за отсутствия Docker/Testcontainers).

Так что обязательно оставляй verify-all.ps1 и локальные хуки — это признак зрелого, профессионального процесса разработки! 😉

Шаг 2: Как лучше оформить коммит и отправить изменения

Теперь, когда мы скорректировали строку подключения к базе данных под требования Google Cloud SQL Socket Factory, мы готовы отправить код в GitHub.



Вопрос про Git Hooks и verify-all.ps1

Когда у меня будет CD, имеется ли теперь смысл от git hooks на пуш и файла verify-all.ps1?



Ответ (для собеседования и практики): Да, смысл определенно есть, и это называется концепцией Shift Left (смещение проверок на более ранние этапы разработки).



Локальный хук / verify-all.ps1 — это ваш первый рубеж обороны. Он проверяет компиляцию, тесты и линтер за пару секунд прямо на вашем компьютере. Вы узнаете об ошибке сразу же, не тратя драгоценные минуты работы раннеров GitHub Actions (которые к тому же имеют лимиты бесплатных минут).

CD Pipeline — это второй, финальный рубеж. Он гарантирует, что в продакшн попадает только полностью валидный код, протестированный в изолированной среде, идентичной серверной.

Рекомендация: Оставьте локальные проверки. Они берегут ваше время и нервы, не позволяя «сломанному» коду улететь в репозиторий.
